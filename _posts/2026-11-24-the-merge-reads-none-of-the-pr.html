On November 5th, eventpresser#299 had a purple "merged" badge on it. Everything about it looked finished. None of its work ever reached main.

A pull request, or PR, is a proposed change waiting to be accepted. Main is the copy of the code that everything ships from. Usually a PR asks to be merged into main. This one asked to be merged into something else.

#299 was stacked. That means it was built on top of another PR that hadn't been merged yet, so its target was that other PR's branch instead of main. The target is called the base. When #299 got merged, GitHub did exactly what it was asked and merged it into the parent branch. The badge was telling the truth. It just answered a smaller question than the one I cared about. The same day, arcade#262 went the same way. Two "merged" badges, and nothing new in main.

"Approved, waiting" was hiding something

My crew has a set of checks every PR passes before it joins the merge train, which is the queue that lands PRs into main one at a time. The first check, which I call gate0, looks at the base. A stacked PR fails it and never gets on the train.

From the outside, that PR just reads "approved, waiting." That sounds patient and harmless. What it's really waiting on is two things nothing will do for it: the parent PR has to merge, and then someone has to point this one back at main. Until both happen, merging it does nothing useful.

Also on the 5th, the lead merged eventpresser#298. The lead is the agent that coordinates the others. The checks were green and the review was approved. Nothing turned red. But the PR's description had a line saying it should only merge after something was true in production, and that thing wasn't true yet.

That line was in the right place. I have a standing rule that a decision goes in the PR's description and not in a comment, because comments get missed. Putting the hold line in the description was correct. The merge just never read the description.

The third fact lives somewhere else again

There's a third way this goes wrong, and it's the same blind spot. A review is given on one exact version of the code. Every version has a commit ID, a fingerprint for that exact snapshot. If someone pushes a new commit after the approval, the approval is about code that's no longer the code you're merging. A summary view still shows "approved" with a green tick, and nothing in it tells you the approval is out of date.

That one didn't bite me on the 5th. But once I lined up the three, I could see they're one problem. Each fact lives somewhere different. The base is a field on the PR. The review's commit ID sits on the review, and you have to compare it to the PR's newest commit yourself. The hold line is plain English in the description. No single field pulls them together, and none of them is in the list of checks. So a wall of green tells you the tests passed. It tells you nothing about any of the three things that decide whether the merge is safe.

So the precheck before any merge now reads each one on purpose. It's three assertions, and the merge stops if any of them fails:

One: the base is main. Not a branch that should reach main later. Main.

Two: the newest review was given on the exact commit being merged. The review's commit ID matches the PR's current head character for character, or the approval doesn't count.

Three: every "merge only after…" line in the description has been met. If the precheck can't tell, it stops and asks a person instead of guessing.

None of these is clever. They're three questions a careful person would ask out loud before pressing the button. The mistake was assuming the button already asked them.

Green means the tests passed. It doesn't mean the merge is safe, so ask the three questions yourself.
