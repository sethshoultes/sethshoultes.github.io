--- title: "How My AI Crew Actually Works" subtitle: "About thirty-five AI agents build and run my projects around the clock. Here's how the work moves, who checks it, and what still comes to me." date: 2026-11-23 ---

People ask me how I keep so many projects moving at once. The honest answer is that I don't do most of the typing anymore. A crew of AI agents does. On a busy night there are about thirty-five of them, some on the computer on my desk and some on a rented server, and they work while I sleep.

That sounds like chaos. It mostly isn't, because the crew runs on a few plain rules. This post walks through them. I've left out the names of the individual projects on purpose. The point is how the work moves, not what it's moving.

Everyone has a lane

Each agent owns one area. One looks after a sign-in service. Another owns a family of small websites. Another handles an events product, another a how-to site, another the servers themselves. When work comes in, it goes to whoever owns that lane.

Two agents don't own the same thing. I learned that the hard way. When two of them worked in the same folder, they quietly undid each other's changes and both reported success. Now every agent works in its own copy of the code, and nobody touches another lane's files.

Above the lanes there are two coordinating roles. One I call the orchestrator. It hands out work, routes reviews, and notices when something has stalled. The other is the lead. It makes the calls the lanes can't make alone, merges finished work, does the jobs that need full access to a server, and writes me a short update every hour.

How one change gets from idea to live

Every change, big or small, takes the same path.

First, the agent that owns the work makes the change and proposes it. A proposed change is a small, self-contained package: what changed, why, and the tests that prove it works.

Second, two other agents read it. They're not the one that wrote it, and they don't run under the same account. One runs on my desk computer and one on the server. They don't just read the code. They break it on purpose. They flip a comparison, delete a safety check, or swap two steps, then run the tests to make sure the tests catch it. If a test still passes with the safety check deleted, the test isn't protecting anything, and that becomes a finding. This one habit has caught more real problems than anything else we do.

Third, if the change touches something where a mistake really costs, it gets one more read from a slower, more careful model. That covers signing in, money, deleting people's data, and passwords and keys. It runs the same break-it-on-purpose test, only deeper. Tonight that deeper read caught a password change that could, in a rare failure, leave someone signed out with no way back in. It also caught a test meant to guard data deletion that had a gap. Both got fixed before they shipped.

Fourth, the change merges only when every automated check is green and the approvals are for the exact version being merged. If anyone adds even one line after a reviewer approved, that approval no longer counts and it gets read again. A record is written at merge time of who approved what, so there's no "I thought someone checked that."

Last, merging is what ships it. The change deploys automatically through the same pipeline every time. Nobody deploys by hand from their own computer.

Rules that keep it honest

A few rules do a lot of the work.

Real data or nothing. If a number isn't real, the page shows a dash and the actual error. It never shows a believable fake. A blank you can see beats a made-up figure you trust.

A failing test is guilty until you read it. Tonight a check failed and I called it a glitch after skimming the noise around it. I hadn't read the actual failing test. It was a real bug, it shipped, and it broke a build for half an hour. Now the rule is simple: read the line that failed before you call anything a fluke. When it happened again an hour later, the failure turned out to point at a possible timing bug, and it got its own investigation instead of a shrug.

Don't overrule a reviewer. If a reviewer says "change this," that stands until the reviewer says otherwise. More than once tonight, waiting would have cost another hour of testing. Even then, the reviewer decided whether a follow-up was good enough. Nobody quietly dismissed it.

Fix the shape, not just the instance. When a privacy tool was recording pages it shouldn't, the first fix tried to switch it off at the right moment. A reviewer showed it could restart itself before the switch took effect. So we rebuilt those pages so the tool never loads on them at all. If something can't happen by design, it doesn't need a guard.

Clean up after yourself. Every test run has a memory limit now, because one runaway run froze the whole server three times in a night. Anything a task starts, it stops before it reports done.

What still comes to me

The crew decides almost everything on its own and tells me afterward. A short list always comes to me first:

  • passwords, keys and access to accounts;
  • anything that spends money;
  • legal questions and pricing;
  • changes to account or security settings;
  • facts only I know.

Tonight that list was two things. Where should a new contact email address forward to? And should a second account be allowed to approve certain changes? Everything else, the agents handled and reported.

Keeping that list short matters. Before it existed, I spent my days answering "is this okay?" questions about things that weren't risky at all. Now the agents decide anything that's easy to undo, and save my attention for the things that aren't.

It works for small jobs too

The same setup handles things that aren't products at all. Tonight a family member needed a game server set up on one of my machines. The crew read his code before running anything. It built the program from his source, never from a download it couldn't check. It ran the server in its own locked-down account, capped how much memory it can use, and opened exactly one network port. It gave it a proper web address and tested it from outside. Then it posted on his project's issue page to tell him it was live.

Now when he needs something, he opens an issue on his own project. A watcher passes it along. Routine requests get handled and answered right there. Anything that touches passwords, new ports, or the rest of the server comes to me first.

What I'd tell you if you're starting

You don't need thirty-five agents. You need the habits. Give each agent one area and don't let two share it. Have someone other than the author read every change, and have them try to break it. Merge only what was actually approved, in the exact form it was approved. Show real data or an honest blank. Write down the short list of things a human must decide, and let the machines decide the rest.

Do those things and adding more agents gets you more done, not more mess.
